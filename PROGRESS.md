## Décisions techniques au-delà de la spec CLAUDE.md

Ces choix ne sont **pas** dans CLAUDE.md d'origine — ils ont été ajoutés en construisant, avec l'accord de l'utilisateur à chaque fois.

### Recherche produit : Google Lens (visuel) + fallback texte, via Vercel Blob
- **Problème résolu** : la recherche texte seule (`google_shopping` via SerpApi) trouvait le bon modèle mais rarement le bon coloris/variante exacte.
- **Solution** : `apps/web/src/lib/serpapi.ts` a deux fonctions — `visualSearch(imageUrl)` (moteur `google_lens` de SerpApi, matching visuel réel sur la photo) essayée en premier, avec repli sur `searchProducts(query)` (texte, `google_shopping`) si la recherche visuelle ne retourne rien.
- **Contrainte découverte** : l'API Google Lens de SerpApi n'accepte qu'une **URL publique**, jamais un fichier uploadé directement.
- **Conséquence architecturale** : `apps/web/src/lib/blob.ts` héberge **toutes** les images sur Vercel Blob avant identification — que ce soit un upload de fichier (`uploadImage`) ou une URL externe capturée par l'extension (`mirrorImageUrl`, qui télécharge puis réhéberge). Les deux flux convergent donc vers une seule URL publique utilisée à la fois pour Claude (vision) et pour Google Lens. `ScannedItem.imageUrl` stocke maintenant une vraie URL Blob, plus jamais de base64 en base.
- **Pourquoi le mirroring est nécessaire même pour les URLs externes** : plusieurs CDN (Pinterest `i.pinimg.com`, les proxies Google, Wikimedia) bloquent le fetcher de Claude via `robots.txt`, alors qu'un simple fetch serveur classique passe sans problème. D'où le passage systématique par notre propre Blob.
- Claude et SerpApi tournent **en parallèle** (`Promise.allSettled`) dans `/api/scan` puisqu'ils ne dépendent que de l'URL de l'image, pas l'un de l'autre — gain de latence.
- Le "thinking" étendu de Claude est désactivé (`thinking: { type: "disabled" }`) dans `lib/anthropic.ts` : tâche de classification simple, pas besoin de raisonnement approfondi.

### Auth Clerk — piège important sur le nom de variable
- **Le bug le plus long à diagnostiquer de tout le build** : Clerk lit sa clé publique en interne via un nom de variable **fixe, non configurable** : `process.env.NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`. Ce n'est pas lié au prop `publishableKey` qu'on passe à `<ClerkProvider>` (qui ne configure que le contexte React côté client) — c'est un constant interne du package `@clerk/nextjs` (`dist/esm/server/constants.js`).
- Si cette variable exacte est absente, `clerkMiddleware()` bascule **silencieusement** en mode "keyless" : aucune vérification de session, aucune erreur, tout le monde traité comme "signed-out" en continuant normalement (pas de redirection). D'où les symptômes déroutants : le dashboard s'affichait sans bloquer un utilisateur non connecté, mais `auth()` renvoyait toujours `userId: null` même après une vraie connexion.
- **Fix** : la variable dans `.env` doit s'appeler exactement `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` (pas `CLERK_PUBLISHABLE_KEY`, contrairement à ce que listait CLAUDE.md à l'origine). `CLERK_SECRET_KEY` (sans préfixe) est correct tel quel.
- **Deuxième piège lié** : `middleware.ts` tourne dans l'**Edge Runtime** de Next.js, qui n'hérite PAS de `process.env` peuplé par notre `require("dotenv")` custom dans `next.config.js` (ça ne marche que pour le runtime Node.js classique — routes API, Server Components). Il faut explicitement réexposer les variables nécessaires à l'Edge via la clé `env` de `next.config.js` :
  ```js
  env: { CLERK_SECRET_KEY: process.env.CLERK_SECRET_KEY }
  ```
  `NEXT_PUBLIC_*` n'a pas besoin de ce traitement — Next.js les auto-injecte partout dès qu'elles sont dans `process.env` au moment du chargement de la config.
- `apps/web/src/lib/auth.ts` : `currentUser()` (API backend de Clerk) n'a **pas** de raccourci `.primaryEmailAddress` (contrairement au hook client `useUser()`) — il faut chercher dans `emailAddresses` via `primaryEmailAddressId` (voir `getPrimaryEmail()`).

### Extension ↔ compte Clerk : lien par cookies partagés
Trois options envisagées (voir conversation) : (1) cookies partagés — simple, non documenté officiellement par Clerk pour ce cas ; (2) SDK officiel `@clerk/chrome-extension` (mode "Sync Host") — robuste mais suppose React/Plasmo dans l'extension, dévie de "sans framework" (CLAUDE.md) ; (3) flux de connexion/jeton custom dans le popup — plus de code à maintenir nous-mêmes. **Option 1 retenue.**
- **Implémentation** : `apps/extension/src/background.ts` envoie `credentials: "include"` sur son `fetch()` vers `/api/scan`. Comme le manifest a déjà `host_permissions` pour le domaine (`http://localhost:3000/*`, `https://scout.app/*`), le cookie de session Clerk part automatiquement si l'utilisateur est connecté au dashboard **dans le même profil Chrome** (pas besoin d'être connecté dans l'extension elle-même). Aucun changement serveur nécessaire — `getOrCreateScanUser()` utilisait déjà `auth()`/`currentUser()`, qui fonctionnent dès que le cookie est présent.
- Si l'utilisateur n'est pas connecté au dashboard dans ce navigateur, le scan reste anonyme (`dev@scout.local`, comme avant) — pas de blocage, dégradation silencieuse.
- **À confirmer par l'utilisateur** : un scan fait par clic-droit doit apparaître dans "Mes scans" une fois connecté. Si les cookies ne passent pas de manière fiable en pratique, basculer vers l'option 2 ou 3 ci-dessus.

### Alertes de prix — prix plancher (au-delà du "toute baisse" prévu par CLAUDE.md)
CLAUDE.md prévoyait juste "un email si le prix baisse". Étendu à la demande de l'utilisateur avec un **prix plancher optionnel** par article de wishlist :
- Schéma : `WishlistItem` a gagné `targetPrice Decimal?` (seuil choisi par l'utilisateur ; si `null`, l'alerte se déclenche sur toute baisse sous `lastKnownPrice`, comportement par défaut) et `alertSentAt DateTime?` (évite de spammer un email chaque jour tant que le prix reste bas — remis à `null` si le prix repasse au-dessus, pour pouvoir re-alerter à la prochaine baisse). Migration : `add_wishlist_target_price`.
- UI : `apps/web/src/app/dashboard/target-price-input.tsx` — petit champ inline sous chaque article de la wishlist ("Définir un prix cible" / "Alerte sous X€"), via `PATCH /api/wishlist/:id`.
- Cron : `GET /api/cron/price-check` (`apps/web/src/app/api/cron/price-check/route.ts`), planifié quotidien via `apps/web/vercel.json`. Logique de revérification : relance `visualSearch()` (Google Lens) sur l'image du scan d'origine, cherche une annonce avec **exactement la même URL marchand** dans les résultats frais (signal le plus fiable pour confirmer que c'est la même offre), compare son prix au seuil. Si aucune correspondance d'URL trouvée dans les résultats frais, l'article est ignoré ce cycle-là (pas de supposition) plutôt que de risquer une fausse alerte.
- **Piège corrigé** : Next.js essaie par défaut de pré-générer les routes API statiquement au build si rien ne les force en dynamique — ce qui aurait exécuté la logique du cron (et envoyé de vrais emails) à **chaque `next build`**. Corrigé avec `export const dynamic = "force-dynamic"` en haut du fichier. Réflexe à appliquer à toute future route avec effets de bord (écriture DB, envoi d'email, appel API payant).
- Protection optionnelle : si `CRON_SECRET` est défini, la route exige `Authorization: Bearer <valeur>`. Vide par défaut pour pouvoir tester manuellement (`curl`) sans friction — à définir avant la mise en production.
- Email : `apps/web/src/lib/resend.ts`, expéditeur `onboarding@resend.dev` (bac à sable Resend, aucune configuration de domaine requise) — **à changer pour une adresse `@scout.app` vérifiée avant la prod**.
- Réponse du cron enrichie avec un compteur `errored` distinct de `skipped` : `skipped` = aucune correspondance d'URL trouvée dans les résultats frais, `errored` = correspondance trouvée mais échec pendant l'enregistrement/l'envoi de l'alerte (ex. Resend mal configuré). Évite de confondre les deux causes lors d'un futur debug.
- **Non fait / hors scope pour l'instant** : disponibilité par taille précise. Nos sources de données (SerpApi/Google Shopping/Google Lens) ne donnent pas le stock par taille — il faudrait scraper individuellement chaque site marchand (fragile, un scraper différent par site). Idée à reconsidérer une fois Awin en place (Phase 4 de PLAN.md), certains flux marchands exposent parfois le stock par taille.

### Paywall — Stripe Checkout + Customer Portal
- `apps/web/src/lib/stripe.ts` : client Stripe singleton, `FREE_SCAN_LIMIT = 5`, mapping `priceIdForPlan`/`planForPriceId` entre les enums `Plan` (`ESSENTIEL`/`PRO`) et les `STRIPE_PRICE_*` d'env.
- `POST /api/stripe/checkout` : requiert une session Clerk (401 sinon — pas de checkout pour l'utilisateur placeholder anonyme). Crée un `Stripe.Customer` au premier appel (sauvegardé sur `User.stripeCustomerId`), sinon le réutilise. Retourne l'URL de la session Checkout (mode `subscription`) ; le front redirige dessus (`window.location.href`).
- `POST /api/stripe/portal` : ouvre le Customer Portal Stripe pour l'utilisateur connecté (404 côté logique si `stripeCustomerId` est encore vide, i.e. jamais payé). Ajouté au-delà du contrat API strict de CLAUDE.md (qui ne liste que `checkout`/`webhook`) car la stack cible explicitement "Stripe Billing (Checkout **+ Customer Portal**)" — sans ça, aucun moyen pour l'utilisateur d'annuler/changer de palier.
- `POST /api/stripe/webhook` : vérifie la signature (`STRIPE_WEBHOOK_SECRET`), écoute `checkout.session.completed` (récupère la subscription associée pour connaître le price payé), `customer.subscription.updated`/`.deleted`. Retrouve le `User` via `stripeCustomerId`, met à jour `User.plan` en conséquence (`FREE` si `canceled`/`unpaid`, sinon mapping du price id). `export const dynamic = "force-dynamic"` (même piège de pré-rendu statique que pour le cron).
- **Limite de scans gratuits** : appliquée dans `/api/scan/route.ts`, **avant** l'appel à Claude/SerpApi (pas après) pour ne pas gaspiller ces appels sur une requête qui va être bloquée. Si `user.plan === "FREE"` et que `ScannedItem.count` du mois civil en cours ≥ `FREE_SCAN_LIMIT`, renvoie `402` avec `{ error, code: "SCAN_LIMIT_REACHED" }`. Le dashboard (`upload-form.tsx`) détecte ce `code` et affiche un encart d'upgrade avec un bouton Checkout direct vers Essentiel ; l'extension affiche le message d'erreur brut dans sa notification (pas d'écran d'upgrade dédié côté extension pour l'instant).
- `FREE_SCAN_LIMIT` (dans `lib/stripe.ts`) abaissé de 5 (spec CLAUDE.md d'origine) à **1**, à la demande de l'utilisateur : stratégie volontairement à friction minimale — pousser la décision gratuit→payant dès le premier scan plutôt qu'après plusieurs usages. `lib/stripe.ts` importe le SDK Node `stripe` (incompatible bundle client) : `FREE_SCAN_LIMIT` ne doit être importé que côté composants serveur (`billing-section.tsx`, `dashboard/page.tsx`) — le composant client `upload-form.tsx` le reçoit en prop plutôt que de l'importer directement, pour ne pas faire fuiter le SDK Stripe dans le bundle navigateur.
- UI dashboard : `dashboard/billing-section.tsx` (palier actuel + compteur `X/5 scans ce mois-ci` si FREE, cartes Essentiel/Pro avec `CheckoutButton` sinon bouton `PortalButton`), `checkout-button.tsx` et `portal-button.tsx` (composants client, POST vers l'API puis redirection `window.location.href` vers l'URL Stripe retournée).
- **Non fait / hors scope pour l'instant** (pas requis par le critère "Terminé quand" de l'étape 6, qui ne porte que sur le blocage du 6ᵉ scan gratuit) : plafond de 15 articles wishlist pour Essentiel, différence digest quotidien (Essentiel) vs temps réel (Pro) dans le cron d'alerte — le cron actuel traite tous les paliers de la même façon. À ajouter si besoin plus tard.
- **À faire côté utilisateur avant de tester** : créer un compte Stripe (mode test), créer deux `Price` récurrents mensuels (Essentiel 6,99€, Pro 11,99€), récupérer `STRIPE_SECRET_KEY` (clé secrète test), lancer `stripe listen --forward-to localhost:3000/api/stripe/webhook` (Stripe CLI) pour obtenir un `STRIPE_WEBHOOK_SECRET` valable en local, puis renseigner les 4 variables (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_ESSENTIEL`, `STRIPE_PRICE_PRO`) dans `.env` et redémarrer `npm run dev`.

### Compte obligatoire avant de scanner (décision au-delà de la spec initiale)
Avec `FREE_SCAN_LIMIT` abaissé à **1** (voir ci-dessus), l'ancien comportement — scan anonyme retombant sur un utilisateur placeholder partagé `dev@scout.local` — cassait la logique métier : ce quota de 1 aurait été partagé par **tous** les utilisateurs anonymes confondus, pas individuel. Corrigé en rendant l'authentification Clerk obligatoire pour scanner, dans les deux flux (dashboard ET extension) :
- `apps/web/src/app/api/scan/route.ts` utilise maintenant `requireUser()` (au lieu de `getOrCreateScanUser()`, supprimé de `lib/auth.ts` avec `DEV_USER_EMAIL`) — 401 + `{ code: "AUTH_REQUIRED" }` si pas de session. Vérifié **avant** tout traitement (avant même de parser le `FormData`), pour ne rien dépenser (Blob, Claude, SerpApi) sur une requête qui sera de toute façon rejetée.
- **Onboarding extension (étape 7)** : `apps/extension/onboarding.html` + `src/onboarding.ts`, 3 écrans (proposition de valeur → comment ça marche → connexion), ouvert automatiquement via `chrome.tabs.create` sur `chrome.runtime.onInstalled` (`details.reason === "install"`). Le dernier écran ouvre `${API_BASE_URL}/sign-in` dans un nouvel onglet ; les deux premiers sont "passables" (bouton Passer), pas le dernier — l'écran de connexion n'est pas un choix, la limite ne marche pas sans compte. Nouvel entry point ajouté au script `build` du `package.json` de l'extension (esbuild).
- `apps/extension/src/background.ts` : les réponses `401 AUTH_REQUIRED` et `402 SCAN_LIMIT_REACHED` déclenchent chacune une notification Chrome avec un **bouton d'action** (`chrome.notifications.create` avec `buttons`, écouté via `chrome.notifications.onButtonClicked`) — "Se connecter" → `/sign-in`, "Voir les paliers" → `/dashboard`. Avant, toute erreur (y compris ces deux cas) tombait dans une notification générique sans action.

### Landing page + funnel de conversion (voir `FUNNEL-PLAN.md` pour le raisonnement complet)
Décision produit de l'utilisateur : friction minimale au premier contact, monétisation quasi immédiate. Implémentation :
- **`apps/web/src/app/page.tsx`** réécrit : nav avec `<ExtensionNavLink>` discret en haut à droite (masqué sur mobile, détection `navigator.userAgent` — Chrome mobile ne supporte pas les extensions) + `<TryWidget>` comme action principale unique, pas de second CTA concurrent.
- **`apps/web/src/app/api/upload/route.ts`** (nouveau) : route publique, **sans authentification**, qui héberge une image sur Vercel Blob (réutilise `uploadImage()` de `lib/blob.ts`) sans jamais appeler Claude/SerpApi. Permet au widget d'essai de laisser déposer une photo avant de demander un compte. Risque connu et accepté pour le MVP : pas de rate-limiting par IP — à ajouter seulement si abusée en pratique.
- **`apps/web/src/components/try-widget.tsx`** (nouveau) : le mur de connexion se déclenche au tout premier clic (bouton "Dépose une photo à identifier"), **avant** même d'ouvrir le sélecteur de fichier — pas après l'upload. Corrigé après un premier essai où l'utilisateur devait attendre la fin de l'upload avant de voir la demande de connexion ; comme rien n'est encore choisi à ce stade, il n'y a rien à faire persister entre-temps (pas de `sessionStorage`, juste `redirect_url=/`). Une fois connecté, le clic suivant ouvre directement le sélecteur de fichier, upload, puis "Identifier ce produit" lance le scan. Résultat affiché avec les mêmes `<WishlistButton>` que le dashboard (réutilisé tel quel via import cross-dossier).
- **`apps/web/src/components/auth-nav-link.tsx`** (nouveau) : lien "Se connecter" (ou "Tableau de bord" si déjà connecté) dans la nav de la landing page — manquant dans la première version, ce qui bloquait un visiteur déjà inscrit qui voulait juste se connecter sans passer par le widget d'essai.
- **`apps/web/src/app/sign-in/[[...sign-in]]/page.tsx`** et `sign-up/[[...sign-up]]/page.tsx` : `forceRedirectUrl` devient dynamique (lu depuis `?redirect_url=`, avec un `safeRedirect()` qui n'autorise que des chemins relatifs commençant par `/` — jamais une URL absolue ou protocol-relative, pour éviter un open redirect). Avant, la valeur était figée à `/dashboard`.
- **Extension 100% payante** : `apps/extension/src/background.ts` envoie l'en-tête `X-Scout-Client: extension` sur son appel à `/api/scan`. Le serveur (`apps/web/src/app/api/scan/route.ts`) bloque *tout* scan venant de ce canal pour un compte `FREE` (`402 EXTENSION_REQUIRES_PLAN`), même le tout premier — le scan gratuit unique ne fonctionne que côté web (dashboard ou widget landing, qui n'envoient pas cet en-tête). L'extension affiche une notification dédiée ("Abonnement requis" → bouton vers `/dashboard`). `apps/extension/onboarding.html` (écran 3) reflète ce choix et ajoute un lien d'échappatoire "Essayer gratuitement sur le web d'abord" vers la landing page — pour ne pas bloquer sèchement quelqu'un qui n'est pas encore prêt à payer.
- **Wishlist et alertes de prix gatées pour de vrai** : jusqu'ici `/api/wishlist` (POST) et `/api/wishlist/:id` (PATCH `targetPrice`) n'avaient **aucune** vérification de palier — n'importe quel compte FREE pouvait déjà les utiliser librement, malgré la doc CLAUDE.md qui les réserve à Essentiel/Pro. Corrigé : les deux renvoient `402 UPGRADE_REQUIRED` pour un compte FREE (sauf remettre `targetPrice` à `null`, qui reste toujours libre — annuler une alerte ne doit jamais être payant). **Changement de comportement sur une fonctionnalité déjà testée** : dans le dashboard existant, cliquer sur ♡ pour un compte FREE affiche maintenant un paywall au lieu de sauvegarder — à re-tester par l'utilisateur.
- **`apps/web/src/components/paywall-prompt.tsx`** (nouveau, partagé) : les deux cartes de palier (Essentiel/Pro), extraites de `billing-section.tsx` pour être réutilisées à 4 endroits (`billing-section.tsx`, `upload-form.tsx`, `wishlist-button.tsx`, `target-price-input.tsx`, `try-widget.tsx`) au lieu d'être dupliquées. `checkout-button.tsx` déplacé de `dashboard/` vers `components/` (n'est plus dashboard-only).
- `FREE_SCAN_LIMIT` (dans `lib/stripe.ts`) abaissé de 5 à **1** avant ce chantier, à la demande de l'utilisateur — voir entrée précédente sur le paywall.
- **Non fait / hors scope pour l'instant** : la landing page en mode "réel" nécessite `EXTENSION_STORE_URL` dans `extension-nav-link.tsx` mise à jour une fois la fiche Chrome Web Store publiée (actuellement un placeholder `https://chrome.google.com/webstore`). Piste future notée mais pas implémentée : intégration PWA "Partager vers Scout" pour un usage mobile natif post-conversion (voir `FUNNEL-PLAN.md`).
- Corrections rapides suite aux premiers tests utilisateur : lien "Se connecter" ajouté à la nav (`auth-nav-link.tsx`, manquait pour un visiteur déjà inscrit), et le mur de connexion du widget se déclenche désormais au tout premier clic sur "Dépose une photo" — avant, non après, l'upload — ce qui a aussi permis de retirer la persistance `sessionStorage` devenue inutile. `UserButton` (menu de compte Clerk, inclut la déconnexion) ajouté à la nav pour pouvoir retester facilement le parcours déconnecté.

### 4ᵉ palier — Scout Découverte (3,99€/mois)
Ajouté à la demande de l'utilisateur, entre Gratuit et Essentiel — objectif : rendre le premier paiement facile à franchir (Zero-Price Effect : le saut de 0€ à n'importe quel prix est le plus dur), tout en donnant une vraie raison de sauter directement à Essentiel ou Pro plutôt que de s'arrêter à Découverte.
- **`Plan` (Prisma)** : nouvel enum `DECOUVERTE` (migration `add_decouverte_plan`).
- **`lib/stripe.ts`** : `PaidPlan` étendu à `"DECOUVERTE" | "ESSENTIEL" | "PRO"`, `priceIdForPlan`/`planForPriceId` généralisés (plus de `if/else` en dur, boucle sur `PAID_PLANS`). Nouveaux exports : `WISHLIST_LIMIT` (plafond wishlist par palier payant, `null` = illimité), `ALERTS_MIN_PLAN` (palier minimum pour les alertes de prix), `planAtLeast()` (comparaison de rang de palier via `PLAN_RANK`).
- **Différenciation réelle, pas juste du texte marketing** — la question posée par l'utilisateur était "comment donner envie de prendre le 2ᵉ ou 3ᵉ palier" ; la réponse retenue est un vrai manque fonctionnel sur Découverte plutôt qu'une simple liste plus courte :
  - **Découverte** : scans illimités + extension débloquée, mais **aucune alerte de prix possible** (`PATCH /api/wishlist/:id` avec un `targetPrice` non nul renvoie `402 UPGRADE_REQUIRED` si le palier n'atteint pas `ALERTS_MIN_PLAN`) et wishlist plafonnée à 5 articles.
  - **Essentiel** : alertes débloquées (vérification quotidienne, via le cron existant), wishlist plafonnée à 15 articles.
  - **Pro** : wishlist illimitée, **et vérification immédiate** du prix dès qu'un prix cible est défini (au lieu d'attendre le cycle quotidien) — implémenté dans `PATCH /api/wishlist/:id` : un appel fire-and-forget à `checkAndAlertWishlistItem()` (voir ci-dessous) juste après la sauvegarde.
  - Ces plafonds (`WISHLIST_LIMIT`) restaurent au passage un morceau de dette technique documenté depuis le début du build : le plafond wishlist Essentiel (15 articles) de la spec CLAUDE.md d'origine n'avait jamais été réellement appliqué.
- **`apps/web/src/lib/price-check.ts`** (nouveau) : la logique de vérification/alerte par article de wishlist, extraite du cron (`checkAndAlertWishlistItem()`), pour être réutilisée à la fois par le cron quotidien (`api/cron/price-check/route.ts`, simplifié en conséquence) et par la vérification immédiate Pro déclenchée depuis `PATCH /api/wishlist/:id`.
- **`components/paywall-prompt.tsx`** : passe de 2 à 3 cartes, chacune avec une liste longue et honnête d'avantages (aucune fonctionnalité listée qui ne soit pas réellement livrée — pas de "score anti-contrefaçon" ni d'"historique de prix" tant que ce n'est pas construit). ### Stratégie de pricing (réflexion avec l'utilisateur, `/pricing`)
- **Prix Pro relevé de 11,99€ à 14,99€/mois** — l'écart avec Essentiel (6,99€) était trop faible (×1,7) pour un vrai effet d'ancrage ("Best" doit généralement être 2-3× "Better" pour rendre le palier du milieu évident par contraste). Fait directement via l'API Stripe : nouveau `Price` créé (`price_1U3IX4Rq9IGBEwy7TNcex39D`, 1499 cents), défini comme `default_price` du produit Pro existant, ancien prix (`price_1U3BkPRq9IGBEwy7vrnJsVvV`) archivé (`active: false`) après ce changement de default — un prix Stripe ne peut pas être modifié une fois créé, ni archivé tant qu'il est le prix par défaut de son produit. `.env` et `paywall-prompt.tsx` mis à jour en conséquence.
- **Décision explicite : ne PAS faire des alertes de prix le levier principal de différenciation entre paliers**, malgré la suggestion initiale d'aligner la métrique de valeur sur la rétention (les alertes créent une raison mensuelle de rester abonné, contrairement aux scans qui sont un geste ponctuel). Raison de l'utilisateur : la fonctionnalité actuelle n'est pas assez aboutie pour miser dessus — l'alerte ne suit qu'**un lien marchand précis** (voir `checkAndAlertWishlistItem` dans `lib/price-check.ts`), pas le produit dans son ensemble tous marchands confondus, et ne gère pas la disponibilité par taille. L'utilisateur considère que la fonctionnalité "vaudra vraiment le coup" seulement quand l'alerte pourra porter sur le produit complet (multi-marchands), pas juste un lien. **En attendant, wishlist + scans restent les différenciateurs principaux entre paliers**, les alertes restent une fonctionnalité présente mais secondaire dans le positionnement.
- **Idée de roadmap notée pour plus tard** (pas construite) : alerte de prix "produit entier" — au lieu de suivre l'URL exacte du marchand d'origine, relancer périodiquement une recherche visuelle et alerter si *n'importe quel* marchand trouvé passe sous le prix cible, pas seulement celui d'origine. Changement non trivial : `checkAndAlertWishlistItem` compare aujourd'hui `freshMatch.url === product.url` précisément — il faudrait plutôt comparer sur l'identité du produit (marque/modèle/coloris) et choisir le moins cher parmi tous les marchands retrouvés, avec un risque réel de faux positif (mauvaise variante confondue) à gérer soigneusement avant de construire ça.

**Plafonds ajustés** (demande utilisateur suite au premier test) — `lib/stripe.ts` a maintenant trois maps distinctes plutôt qu'une constante unique :
- `SCAN_LIMIT` : FREE 1, Découverte 9, Essentiel 25, Pro illimité. `/api/scan` applique désormais ce plafond à **tous** les paliers (avant : uniquement FREE) ; le message d'erreur est généré dynamiquement selon le palier.
- `WISHLIST_LIMIT` : inchangé (5/15/illimité).
- `ALERT_LIMIT` (nouveau, remplace `ALERTS_MIN_PLAN`/`planAtLeast`) : Découverte 0 (bloqué, comme avant), Essentiel **5 alertes actives max**, Pro illimité. `PATCH /api/wishlist/:id` compte les `WishlistItem` avec un `targetPrice` non nul pour l'utilisateur, mais seulement quand l'alerte est **nouvelle** (l'item n'avait pas déjà de `targetPrice`) — modifier le seuil d'une alerte existante ne recompte pas contre le plafond.
- `EXCLUDE_PLANS_FOR` (nouveau, partagé) : remplace la map locale dupliquée qui existait dans `billing-section.tsx`.
- Les messages d'erreur du serveur (`body.error`) sont maintenant affichés tels quels côté client (`wishlist-button.tsx`, `target-price-input.tsx`, `upload-form.tsx`) au lieu d'un texte générique codé en dur — évite le décalage qui serait apparu entre le vrai plafond (variable selon le palier) et un message client figé sur "scan gratuit".

## Problèmes connus / dette technique

- **Wishlist toujours un peu lente au clic**, même si le cœur se met à jour visuellement à l'instant (mise à jour optimiste côté client dans `wishlist-button.tsx`). La requête réseau réelle en arrière-plan reste lente : `requireUser()` fait un aller-retour vers l'API de Clerk (`currentUser()`) PUIS un upsert Prisma vers Neon (pooled, hébergé) — au moins deux aller-retours réseau externes par action. Pas corrigé plus loin, jugé acceptable pour le MVP puisque le retour visuel est instantané.
- La section "Wishlist" en bas du dashboard se resynchronise via `router.refresh()` en arrière-plan après chaque clic — peut donc avoir un léger délai avant d'apparaître dans la liste complète, même si le cœur du produit concerné est déjà à jour.
- Prisma CLI est resté bloqué plusieurs fois avec `EPERM` sur `query_engine-windows.dll.node` pendant que `npm run dev` tournait (Windows verrouille le fichier) — sans gravité, il suffit de relancer `npm install` (le paquet s'installe quand même, seul le `postinstall` échoue).
- `.next` (cache de build) a dû être supprimé manuellement une fois pendant le debug Clerk (`PageNotFoundError` fantôme sur une route qui existait bien) — si un comportement bizarre et incohérent avec le code source apparaît, `rm -rf apps/web/.next` puis redémarrer est le premier réflexe.
